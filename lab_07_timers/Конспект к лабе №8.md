## Вопросы в конце методички

### 1. Что такое операционная система реального времени?
**Операционная система реального времени** (англ. _Real-Time Operating System_, RTOS) — это специализированная операционная система, предназначенная для управления вычислительными ресурсами с гарантированным временем отклика на внешние события. В отличие от универсальных ОС (Windows, Linux), где приоритетом является максимальная пропускная способность, в RTOS критическим параметром выступает **детерминизм** — предсказуемость временных характеристик выполнения задач.

### 2. Что такое CMSIS-RTOS?
**CMSIS-RTOS** (Cortex Microcontroller Software Interface Standard - Real Time Operating System) — это стандарт API (интерфейс программирования приложений), разработанный компанией **Arm**.

Простыми словами: это **«универсальный пульт управления»** для любой операционной системы реального времени (RTOS), работающей на микроконтроллерах Cortex-M (как ваш STM32H7).
#### Зачем это нужно?
Представьте, что вы написали сложное приложение, используя функции конкретной ОС, например **FreeRTOS**.
- Если вы захотите перейти на другую ОС (например, **RTX** от Keil или **Azure RTOS**), вам придется переписывать весь код, потому что функции называются по-разному (`xTaskCreate` в FreeRTOS против `os_tsk_create` в RTX).
#### CMSIS-RTOS решает эту проблему.
Если вы пишете код, используя стандартные функции CMSIS-RTOS (например, `osThreadNew`), то этот код будет работать на **любой** RTOS, для которой есть адаптер CMSIS. Вам не нужно менять код приложения — вы просто меняете «прослойку» (адаптер) в настройках проекта.
### 3. Назовите 3 свойства операционной системы FreeRTOS.
Вот три ключевых свойства операционной системы **FreeRTOS**, которые отличают её от универсальных ОС (таких как Windows или Linux) и от простого программного кода (bare-metal):
1. Вытесняющая многозадачность с приоритетами (Preemptive Priority Scheduling)
2. Детерминизм (Поведение реального времени)
3. Малый размер и модульность (Small Footprint)
### 4. Что такое вытеснение контекста? Какие исключения и ресурсы используются для его реализации?
**Вытеснение контекста** определяется как процесс приостановки выполнения текущей задачи (thread/task) операционной системы реального времени (ОСРВ) с последующим возобновлением выполнения другой задачи, обладающей более высоким приоритетом или готовой к выполнению. Данный процесс заключается в сохранении состояния исполнительного потока текущего процесса в оперативную память (в область, называемую «стек задачи») и восстановлении состояния новой задачи из ее области хранения.
#### Используемые исключения (Exception Handling)
В микроконтроллерах семейства ARM Cortex-M реализация непротиворечивого переключения контекста опирается на специфическую архитектуру обработки исключений. Используются следующие ключевые механизмы:
- **PendSV (Pending Vectored System Call):** Это программно-инициируемое системное исключение с минимальным приоритетом среди всех обработчиков системных вызовов. Оно используется планировщиком ОСРВ для фактического выполнения операции переключения стеков. Установка флага PendSV откладывает выполнение переключения до момента завершения всех прерываний с более высоким приоритетом (например, таймера или приема данных), что минимизирует время отклика и накладные расходы.
- **SysTick Timer (Таймер тактовой частоты):** Исключение, генерируемое встроенным снизительным счетчиком. Периодические прерывания этого таймера используются для вызова функции планировщика (`vTaskSwitchContext()`), которая инициирует запрос на переключение через флаг PendSV.
- **Аппаратное сохранение состояния (Hardware Auto-Save):** При возникновении любого внешнего прерывания (HardFault, NMI, внешнее IRQ) контроллер прерываний (NVIC) автоматически сохраняет содержимое регистров R0–R3, R12, LR, PC и xPSR в стек текущего режима работы (Thread Mode) перед передачей управления обработчику прерывания. Это позволяет выполнить код обработчика без явного программного сохранения контекста задачи, которую он вытеснил.
#### Используемые ресурсы
Для корректного функционирования вытеснения требуется выделение и управление следующими аппаратными ресурсами:
- **Память (Стек задачи — Task Stack):** Для каждой управляемой задачей выделяется отдельный участок статической памяти в ОЗУ. Объем данного участка рассчитывается таким образом, чтобы вместить все необходимые регистры при переключении контекста.
- **Общий регистр указателя (MSP / PSP):**
    - **MSP (Main Stack Pointer):** Используется во время работы ядра ОСРВ и обработчиков исключений.
    - **PSP (Process Stack Pointer):** Активируется (через бит CTRL bit 1 регистра CONTROL) когда задача переходит в состояние Thread Mode. При переключении задач происходит изменение значения регистра CONTROL, что приводит к автоматическому переносу указателя SP со стека одной задачи на стек другой.
- **Блок NVIC (Nested Vectored Interrupt Controller):** Аппаратный модуль, отвечающий за арбитраж прерываний. Он обеспечивает логическое определение приоритета и гарантирует атомарность операций сохранения контекста при входе в режим обработчика (Handler Mode).
### 5. Какая информация хранится в блоке управления потоком (TCB)?
**Блок управления потоком (TCB, Thread Control Block)** — это внутренняя структура данных ядра операционной системы (или ОСРВ), которая хранит всю информацию, необходимую для управления задачей, её планирования и восстановления состояния после переключения контекста. TCB создаётся при создании задачи и уничтожается при её завершении.
В типичной реализации (в том числе в FreeRTOS, RTX, Zephyr и др.) TCB содержит следующие категории данных:
- **Идентификация и метаданные**
- **Состояние и приоритет**
- **Аппаратный контекст (сохраняется при переключении)**
- **Управление стеком**
- **Информация для планировщика**
- **Ресурсы и механизмы синхронизации**
- **Учёт, отладка и расширения**

### 7. Какие механизмы контроля ошибок при работе с памятью имеются во FreeRTOS?
В FreeRTOS существует несколько уровней механизмов контроля ошибок, связанных с памятью. Поскольку в микроконтроллерах (например, STM32H7) нет встроенного MMU (блока управления памятью) для изоляции процессов, как в Linux или Windows, контроль возложен на программный уровень и конфигурацию ядра.
Основные механизмы:
1. **Защита от переполнения стека задачи (Stack Overflow Detection)**. Это самая распространенная ошибка. Если локальных переменных слишком много или происходит слишком глубокий вызов функций, стек задачи выходит за выделенные границы и перезаписывает память других задач или управляющие структуры ядра.
2. **Управление кучей (Heap Management) и проверка целостности**. 
3. **Hook-функции (Крючки) для отладки**
4. **Внутренние проверки (Asserts)**
5. **MPU (Memory Protection Unit) - Аппаратная защита**
### 8. Зачем нужна отложенная обработки прерываний и как она реализуется?
**Отложенная обработка прерываний** (Deferred Interrupt Processing) — это метод проектирования программного обеспечения встраиваемых систем, при котором код обработчика прерывания (ISR) делится на две части: быструю (критичную по времени) и медленную (выполняемую в фоновом режиме).
Основная цель — **минимизировать время нахождения в контексте прерывания**.
Если обработчик прерывания (ISR) выполняется слишком долго (например, содержит сложные вычисления, циклы или задержки), возникают следующие проблемы:
1. **Блокировка других прерываний:** В большинстве архитектур (включая ARM Cortex-M) во время выполнения ISR прерывания с тем же или меньшим приоритетом блокируются. Если ISR долгий, система становится "глухой" к новым событиям.
2. **Высокая задержка (Interrupt Latency):** Время от момента возникновения аппаратного события до начала реакции на него увеличивается. Для систем реального времени это критично.
3. **Невозможность использования блокирующих функций:** В контексте прерывания нельзя использовать функции, которые переводят задачу в состояние ожидания (например, `vTaskDelay` или ожидание мьютекса), так как это подвесит всё ядро ОС.
#### Как это реализуется?
Процесс делится на две фазы:
##### Фаза 1: Верхняя половина (Top Half) — Контекст прерывания
##### Фаза 2: Нижняя половина (Bottom Half) — Контекст задачи
#### Реализация во FreeRTOS
В среде FreeRTOS отложенная обработка реализуется через **межзадачные примитивы синхронизации**.
### 9. Какие алгоритмы планирования поддерживает FreeRTOS?
FreeRTOS поддерживает **несколько режимов планирования**, которые выбираются на этапе компиляции через конфигурационный файл `FreeRTOSConfig.h`. В отличие от универсальных ОС, FreeRTOS не переключает алгоритмы динамически; вместо этого разработчик выбирает один из следующих режимов:
 1. Вытесняющее планирование с фиксированными приоритетами (Preemptive Fixed-Priority Scheduling)
 2. Кооперативное планирование (Cooperative Scheduling)
 3. Квантование времени / Round-Robin (Time Slicing)
### 10. Какие параметры задаются при создании задачи и какие могут быть изменены в дальнейшем?
В операционных системах реального времени (в частности, во **FreeRTOS**, которая используется в вашем контексте) параметры задачи делятся на **фиксируемые при создании** и **динамически изменяемые во время выполнения**.
#### Параметры, задаваемые при создании задачи

|Параметр|Описание|Изменяемость|
|---|---|---|
|**Функция задачи** (`TaskFunction_t`)|Точка входа, код, который будет выполняться в цикле `while(1)`|❌ Невозможно изменить|
|**Имя задачи** (`pcName`)|Строка для отладки, трассировки и профилирования (до 16 символов по умолчанию)|❌ Невозможно изменить|
|**Размер стека** (`usStackDepth`)|Количество слов (4 байта на ARM) под стек задачи. Определяет объём локальных переменных и глубину вызовов|❌ Невозможно изменить (динамическое расширение стека в FreeRTOS не поддерживается)|
|**Параметры/аргументы** (`pvParameters`)|Указатель на данные, передаваемые в задачу при старте|🔹 Сам указатель фиксирован, но **данные по нему могут меняться**, если задача и создающий код синхронизированы|
|**Приоритет** (`uxPriority`)|Число от `0` (низший) до `configMAX_PRIORITIES-1` (высший). Определяет порядок планирования|✅ Можно изменять в runtime|
|**Дескриптор (Handle)** (`pxCreatedTask`)|Указатель на блок управления задачей (TCB). Возвращается после создания|❌ Невозможно изменить (но можно получить через `xTaskGetHandle()`)|
#### Параметры, которые можно изменить во время выполнения
|Параметр|API FreeRTOS|Примечание|
|---|---|---|
|**Приоритет**|`vTaskPrioritySet(TaskHandle_t, UBaseType_t)`|Может применяться только к задаче, отличной от вызывающей (или к себе через `xTaskGetCurrentTaskHandle()`). Изменение приоритета выше текущего может вызвать немедленное вытеснение.|
|**Состояние выполнения**|`vTaskSuspend()` / `vTaskResume()` / `vTaskDelete()`|Задача может приостановить себя или другую. `vTaskDelete()` освобождает память (если задача создана динамически).|
|**Значение уведомления** (`ulNotifiedValue`)|`vTaskNotifyGive()`, `xTaskNotify()`, `ulTaskNotifyGiveIndexed()`|Хранится в TCB. Используется как быстрый аналог семафора или флага без выделения дополнительных объектов.|
|**Время до следующего пробуждения**|`vTaskDelay()`, `vTaskDelayUntil()`|Относительная или абсолютная задержка. Планировщик автоматически переводит задачу в состояние `Blocked`, а затем в `Ready`.|
|**Привязка к объектам ядра**|`xQueueSend()`, `xSemaphoreTake()`, `xEventGroupSetBits()`|Динамическое взаимодействие с очередями, мьютексами, группами событий. Не меняет TCB напрямую, но влияет на состояние задачи.|
### 11. Что такое Мьютекс. Чем отличается рекурсивный мьютекс от обычного?
**Мьютекс** (от англ. **Mut**ual **Ex**clusion — взаимное исключение) — это механизм синхронизации, который гарантирует, что доступ к общему ресурсу (переменной, устройству, файлу) имеет только **одна** задача одновременно.
Это похоже на **ключ от туалета**:
- Чтобы зайти в туалет, нужно взять ключ.
- Если ключ у вас — туалет занят (мьютекс захвачен).
- Другой человек не может зайти, пока вы не выйдете и не повесите ключ обратно (отпустите мьютекс).
#### Главная особенность Мьютекса (отличие от Семафора)
Ключевое свойство мьютекса — **принадлежность (Ownership)**.
- Захватить мьютекс может любая задача.
- **Освободить (отпустить) мьютекс может только та задача, которая его захватила.**
- Если задача попытается освободить чужой мьютекс, это считается ошибкой программирования.
#### Обычный мьютекс vs Рекурсивный мьютекс
Разница заключается в том, как система реагирует, если **одна и та же задача** пытается захватить мьютекс повторно (вложенный вызов).
##### Обычный мьютекс (Non-recursive)
- **Поведение:** Если задача `A` уже захватила мьютекс и пытается захватить его снова (не отпустив первый раз), произойдет **тупик (Deadlock)** или ошибка.
- **Логика:** Ядро ОС не различает, _кто_ пытается захватить мьютекс снова. Для него мьютекс уже занят.
- **Применение:** Простые случаи, где функции не вызывают друг друга внутри критической секции.
##### Рекурсивный мьютекс (Recursive Mutex)
- **Поведение:** Если задача `A` уже захватила мьютекс и пытается захватить его снова, операция **успешна**.
- **Механизм:** Внутри мьютекса скрыт **счетчик вложенности**.
    1. Задача `A` берет мьютекс -> Счетчик = 1.
    2. Задача `A` берет мьютекс снова -> Счетчик = 2.
    3. Чтобы ресурс стал доступен другим задачам, задача `A` должна **отпустить мьютекс столько же раз, сколько она его взяла** (сбросить счетчик в 0).
- **Применение:** Сложная логика, где функции вызывают друг друга (рекурсия), и обе функции нуждаются в доступе к одному ресурсу.
### 12. Какие схемы управления динамической памятью имеются во FreeRTOS?
Во FreeRTOS для управления динамической памятью (кучей, heap) не используется стандартная библиотека C (`malloc`/`free`), так как она часто не является потокобезопасной и может работать недетерминированно. Вместо этого FreeRTOS предлагает **5 различных схем управления памятью**, реализованных в файлах `heap_1.c`, `heap_2.c`, `heap_3.c`, `heap_4.c` и `heap_5.c`.
1. Heap_1 (**Простейшая схема**)
2. Heap_2 (**Best Fit — Наилучшее совпадение**)
3. Heap_3 (**Обертка над стандартной библиотекой**)
4. Heap_4 (**Coalescing Best Fit**)
5. Heap_5 (**Множественные области памяти**)
### 13. Какие функции блокировки по времени существуют во FreeRTOS и чем они отличаются?
В FreeRTOS время измеряется в **тиках системного таймера** (SysTick). Все функции блокировки по времени работают с этим базовым тактом. Конвертация в миллисекунды выполняется макросом `pdMS_TO_TICKS(ms)`.
#### Основные функции задержки

|Функция|Тип отсчёта|Поведение|Когда использовать|
|---|---|---|---|
|`vTaskDelay(const TickType_t xTicksToDelay)`|**Относительный**|Блокирует задачу минимум на `xTicksToDelay` тиков _с момента вызова_. Фактическая пауза может быть длиннее из-за вытеснения, задержек прерываний или выравнивания по границе тика.|Простые паузы, энергосбережение, опрос с допустимым джиттером.|
|`vTaskDelayUntil(TickType_t *pxPreviousWakeTime, const TickType_t xTimeIncrement)`|**Абсолютный (периодический)**|Пробуждает задачу строго через `xTimeIncrement` тиков _от предыдущего пробуждения_. Автоматически компенсирует время выполнения кода задачи внутри цикла. Корректно обрабатывает переполнение счётчика тиков.|Жёстко периодические задачи: управление, сбор данных с фиксированной частотой, PID-регуляторы.|
|`xTaskDelayUntil(...)` (FreeRTOS v10+)|**Абсолютный + статус**|Полностью аналогична `vTaskDelayUntil`, но возвращает `pdTRUE` (успешно) или `pdFALSE` (запрошенное время пробуждения уже прошло или произошло переполнение/пропуск тика).|Критичные системы, где нужно детектировать пропущенные циклы или рассинхронизаци|
### 14. Каким образом конфигурируется FreeRTOS для аппаратной среды и нужд приложения?
Конфигурация FreeRTOS для конкретной аппаратной платформы и требований приложения выполняется через **единственный заголовочный файл `FreeRTOSConfig.h`**. Он является «центром управления» ядром: определяет архитектуру, параметры планировщика, объём памяти, набор доступных примитивов синхронизации и отладочные возможности.
### 15. Зачем нужна отложенная обработка прерываний в ОСРВ?
Отложенная обработка прерываний нужна для того, чтобы разделить задачи на две категории: **срочные** (которые должен выполнить контроллер мгновенно) и **длительные** (которые требуют много вычислительного времени).
В контексте операционной системы реального времени это необходимо по следующим причинам:
1. Минимизация времени простоя (Interrupt Latency)
2. Разблокировка остальных прерываний
3. Возможность использования стандартных функций
### 16. Опишите схему реализации отложенной обработки прерываний.
Схема реализации отложенной обработки прерываний (Deferred Interrupt Processing) в ОСРВ базируется на разделении работы на две фазы: **быструю** (в контексте прерывания) и **медленную** (в контексте задачи).
Процесс обработки внешнего события делится на три основных этапа:
#### Этап А: "Верхняя половина" (Top Half) — Обработчик прерывания (ISR)
Это функция, выполняемая процессором в момент возникновения аппаратного события (например, принят байт по UART).
- **Цель:** Максимально быстро обслужить аппаратуру.
- **Ограничения:** Нельзя вызывать блокирующие функции (очереди, задержки, мьютексы).
- **Действия:**
    1. Считать данные из регистра периферии (чтобы сбросить флаг прерывания).
    2. Сохранить данные в оперативную память (буфер).
    3. **Послать сигнал (Notification)** задаче-обработчику ("Нижней половине"), что работа есть.
    4. Запросить переключение контекста (если задача-обработчик имеет более высокий приоритет).
#### Этап Б: Переключение контекста (Контекстный мост)
Планировщик ОСРВ (FreeRTOS) перехватывает управление. Он видит, что ISR "разбудил" высокоприоритетную задачу.
- Процессор переключается из режима **Handler Mode** (прерывание) в режим **Thread Mode** (задача).
- Обычно это происходит через исключение **PendSV** (Pending System Call).
#### Этап В: "Нижняя половина" (Bottom Half) — Задача (Task)
Это обычная функция потока, которая работает в цикле.
- **Цель:** Выполнить сложную обработку данных без ограничений по времени.
- **Действия:**
    1. Находится в состоянии `Blocked` (ожидание), пока ISR не пришлет сигнал.
    2. Просыпается при получении сигнала.
    3. Берет данные из буфера/очереди.
    4. Выполняет долгую логику (парсинг, математика, вывод на экран, запись на флешку).
    5. Возвращается в состояние `Blocked`.
### 17. Что такое семафор? Чем отличается бинарный семафор от счетного семафора?
**Семафор** — это механизм синхронизации, используемый в операционных системах (в том числе в FreeRTOS) для управления доступом к общим ресурсам или для передачи сигналов между задачами.
Проще всего представить семафор как **набор жетонов** или **ключей**:
- Чтобы войти в критическую секцию или начать действие, задача должна **«Взять» (Take)** жетон.
- Если жетонов нет, задача блокируется (засыпает) и ждет.
- Когда ресурс освобождается или событие происходит, другой поток **«Отдает» (Give)** жетон обратно, и ждущая задача просыпается.
#### Бинарный семафор (Binary Semaphore)
Это самый простой вид семафора. Он может находиться только в **двух состояниях**:
- **1 (Available / Отдан):** Жетон свободен, задача может его взять.
- **0 (Empty / Взят):** Жетон занят, задача должна ждать.
**Аналогия:** Представьте **ключ от туалета**.
- Ключ либо висит на крючке (состояние 1), либо находится у кого-то в кармане (состояние 0).
- Нельзя иметь два ключа от одного туалета одновременно.
**Применение во FreeRTOS:**
- **Синхронизация задач:** Одна задача (например, обработчик прерывания) сигнализирует другой задаче, что событие произошло (например, "данные пришли по UART").
- **Взаимное исключение:** Защита доступа к устройству (например, чтобы две задачи не писали в UART одновременно), хотя для этого лучше подходит Мьютекс.
**Особенность:** Если вы попытаетесь «Отдать» (`Give`) бинарный семафор, который уже «Отдан», операция проигнорируется (счетчик не станет равен 2).
#### Счетный семафор (Counting Semaphore)
Этот семафор хранит **целое число**, которое может меняться в диапазоне от `0` до заданного максимума (`N`).
**Аналогия:** Представьте **парковку на 5 мест**.
- Счетчик показывает количество свободных мест (максимум 5).
- Когда заезжает машина, счетчик уменьшается.
- Когда машина уезжает, счетчик увеличивается.
- Если счетчик равен 0, новые машины (задачи) должны ждать на въезде.
#### Главные отличия (Таблица)

| Характеристика                 | Бинарный семафор                            | Счетный семафор                                               |
| ------------------------------ | ------------------------------------------- | ------------------------------------------------------------- |
| **Значение счетчика**          | Только **0** или **1**                      | От **0** до **N** (где N — максимальный предел)               |
| **Основная цель**              | Синхронизация (Сигнал "Сделано" / "Готово") | Управление группой идентичных ресурсов или накопление событий |
| **Поведение при переполнении** | Игнорирует повторный `Give`, если уже 1     | Позволяет `Give` до достижения максимума                      |
| **API FreeRTOS**               | `xSemaphoreCreateBinary()`                  | `xSemaphoreCreateCounting(max, initial)`                      |
### 18. Чем отличается мьютекс от бинарного семафора?

### 19. Что такое очередь в ОСРВ. В каких ситуациях задачи могут блокироваться на очереди?
**Очередь (Queue)** в операционной системе реального времени (например, FreeRTOS) — это механизм обмена данными между задачами, а также между задачами и обработчиками прерываний (ISR).
В отличие от обычных структур данных, очереди в RTOS обладают специфическими свойствами, делающими их пригодными для многозадачной среды:
1. **Потокобезопасность (Thread-Safe):** Доступ к очереди защищен внутренними мьютексами. Несколько задач могут пытаться записать в одну очередь или читать из неё одновременно без риска повреждения данных (race conditions).
2. **Копирование данных:** Когда задача отправляет данные в очередь, они **копируются** внутрь буфера очереди. Когда другая задача читает данные, они снова **копируются** из буфера в переменную задачи.
    - _Важно:_ Обычно передаются значения (структуры, числа), а не указатели, чтобы избежать проблем, если отправитель удалит свои данные до того, как получатель их считает.
3. **Принцип FIFO:** По умолчанию данные извлекаются в том же порядке, в котором были помещены (Первым пришел — первым ушел).
4. **Размер:** При создании очереди задаются параметры:
    - `xLength`: Количество элементов, которое может хранить очередь (глубина).
    - `xItemSize`: Размер одного элемента в байтах (например, `sizeof(uint32_t)` или `sizeof(MyStruct)`).
#### В каких ситуациях задачи блокируются на очереди?
Блокировка (перевод задачи в состояние `Blocked`) происходит, когда задача пытается выполнить операцию с очередью, но **условия для немедленного выполнения не соблюдены**.
Существует два основных сценария блокировки:
##### 1. Блокировка при ЧТЕНИИ (Задача хочет получить данные)
Задача вызывает функцию приема (например, `xQueueReceive`), но **очередь пуста**.
- **Ситуация:** Ядро CM7 хочет прочитать хокку, но ядро CM4 ещё не отправило ни одного, или отправило всё, что было в буфере.
- **Действие ОСРВ:** Поскольку читать нечего, задача переводится в состояние `Blocked`. Она освобождает процессорное время и не потребляет ресурсы CPU.
- **Разблокировка:** Задача проснется только тогда, когда другая задача (или прерывание) положит данные в эту очередь (функция `xQueueSend`).
##### 2. Блокировка при ЗАПИСИ (Задача хочет отправить данные)
Задача вызывает функцию отправки (например, `xQueueSend`), но **очередь переполнена** (в ней нет свободного места).
- **Ситуация:** Ядро CM4 генерирует хокку быстрее, чем CM7 успевает их обрабатывать и забирать. Буфер очереди заполнен до предела.
- **Действие ОСРВ:** Задача переводится в состояние `Blocked`, чтобы не потерять данные (так как очередь имеет фиксированный размер).
- **Разблокировка:** Задача проснется, когда другая задача освободит место в очереди, прочитав оттуда старые данные.
### 20. Какие функции для работы с очередями предоставляет FreeRTOS?
#### 1. Создание и удаление очередей
Эти функции вызываются **до** запуска планировщика (или в рамках задачи-инициализатора).
- `xQueueCreate( UBaseType_t uxQueueLength, UBaseType_t uxItemSize )`
    - Динамически выделяет память в куче FreeRTOS для очереди.
    - Возвращает `QueueHandle_t` (дескриптор), который используется во всех остальных функциях.
- `xQueueCreateStatic(...)`
    - Создает очередь, используя заранее выделенную пользователем память (без выделения из кучи). Полезно для систем с жесткими требованиями к памяти.
- `vQueueDelete( QueueHandle_t xQueue )`
    - Удаляет очередь и освобождает выделенную под нее память.
#### 2. Отправка данных (из задач)
Эти функции блокируют задачу, если очередь полна (если не указан таймаут `0`).
- `xQueueSend( xQueue, pvItemToQueue, xTicksToWait )`
    - Помещает элемент в **конец** очереди (FIFO). Эквивалент `xQueueSendToBack`.
- `xQueueSendToFront( xQueue, pvItemToQueue, xTicksToWait )`
    - Помещает элемент в **начало** очереди. Полезно для передачи данных с высоким приоритетом (LIFO).
- `xQueueSendToBack( xQueue, pvItemToQueue, xTicksToWait )`
    - Явная запись в конец очереди.
- `xQueueOverwrite( xQueue, pvItemToQueue )`
    - Перезаписывает данные в очереди, если она полна. Полезно, когда нужно всегда иметь «самое свежее» значение (например, состояние датчика), и старые данные не важны.
#### 3. Получение данных (из задач)
Эти функции блокируют задачу, если очередь пуста.
- `xQueueReceive( xQueue, pvBuffer, xTicksToWait )`
    - Читает элемент из начала очереди и **удаляет** его оттуда.
    - `pvBuffer` — указатель на переменную, куда будут скопированы данные.
- `xQueuePeek( xQueue, pvBuffer, xTicksToWait )`
    - Читает элемент из начала очереди, но **не удаляет** его (просмотр). Следующее чтение получит те же данные.
#### 4. Работа из прерываний (ISR) — Критически важно!
Внутри обработчиков прерываний (ISR) **запрещено** использовать обычные функции, так как они могут вызывать блокировки. Используются специальные версии с суффиксом `FromISR`.
- `xQueueSendFromISR( xQueue, pvItemToQueue, pxHigherPriorityTaskWoken )`
    - Отправляет данные в очередь из прерывания.
    - **Важно:** Если задача, ожидающая данные, имеет приоритет выше текущего, этот параметр сигнализирует планировщику о необходимости переключения контекста сразу после выхода из прерывания.
- `xQueueReceiveFromISR( xQueue, pvBuffer, pxHigherPriorityTaskWoken )`
    - Принимает данные из очереди внутри прерывания.
#### 5. Вспомогательные функции (Статус и управление)
- `uxQueueMessagesWaiting( xQueue )`
    - Возвращает количество элементов, находящихся в очереди в данный момент.
- `uxQueueSpacesAvailable( xQueue )`
    - Возвращает количество свободных мест в очереди.
- `xQueueReset( xQueue )`
    - Очищает очередь, делая ее снова пустой (все данные теряются).
- `xQueueIsQueueFullFromISR( xQueue )`
    - Быстрая проверка на заполненность из контекста прерывания.
### 21. Что такое критическая секция кода.
**Критическая секция (Critical Section)** — это участок программы, который работает с **общими ресурсами** (переменными, регистрами периферии, буферами в памяти) и должен выполняться **непрерывно и эксклюзивно**, то есть в один момент времени внутри него может находиться только один поток исполнения (задача или обработчик прерывания).
